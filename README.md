# MediRemind — Smart Patient Medication & Refill Tracker

A full-stack web app that helps patients track daily medication doses, keep an accurate
remaining-quantity count, and get refills **before** they run out. Chemists fulfil refill
requests through a dedicated console, and family caregivers get read-only, scope-limited
visibility — only with the patient's explicit consent, revocable at any time.

This is a complete working application: real database, real authentication, real server-side
authorization, and automated tests. It is **not** a static mock-up or a landing page.

## What works

Everything listed here was exercised end-to-end in a browser against the running server.

**Authentication & accounts**

- Email + password registration and login (bcrypt, 12 rounds; only the hash is stored).
- Session-based auth via `express-session` with `httpOnly` cookies (`sameSite=lax` in
  development, `sameSite=none` + `secure` in production for cross-domain deployments).
- Rate limiting on authentication routes.
- Password change (requires the current password) and profile editing.
- Login failures never reveal whether an email address exists.

**Patients**

- Create/edit medications: name, prescribed dose, dose unit, schedule times, frequency,
  quantity per dose, current stock, quantity unit, refill threshold, start/end dates.
- Pause, resume, or mark a medication as ended.
- Today's schedule with **Taken / Skip / Snooze** actions; snooze re-arms the reminder.
- Dose history and adherence reports with date-range and status filters.
- Inventory view: remaining quantity, estimated days left, status
  (`IN_STOCK` / `LOW_STOCK` / `REFILL_REQUIRED`), an auditable ledger, and manual stock
  corrections for physical counts.
- Refill requests: create, track progress, cancel. Only one active request per medication.
- CSV export of dose history.

**Chemists**

- Accounts cannot self-register. They are provisioned out-of-band with
  `npm run provision:chemist`.
- Console showing only requests routed to their own shop (patient data from other shops
  returns 404, not 403 — no existence leak).
- Actions: **Accept → Mark ready → Complete & add stock**, plus **Reject** (with a reason
  shown to the patient) and **Cancel** (withdraw before any stock is supplied).
- Completing a refill is the only action that increases patient stock, and it is
  double-confirmation-proof at the database level.
- Confirmed transactions list, and a list of patients who linked to their shop.

**Caregivers**

- Self-register as caregivers, but see **nothing** until a patient invites them *and*
  they accept.
- Invitations carry per-category scopes (adherence, missed doses, upcoming doses, refills,
  inventory) that the patient can change at any time.
- Revoking access takes effect immediately (`ACTIVE` → `REVOKED`).
- Only caregiver-role accounts can be invited; inviting a patient or chemist account is
  rejected.

**Notifications**

- In-app notifications generated by real events (low stock, refill status changes,
  caregiver invitations), with a bell menu and "mark all read".

## Quick start

Requirements: **Node.js 20+** and npm. Nothing else — the dev database is a local SQLite
file that is created for you.

```bash
# 1. Install dependencies for both workspaces
npm install

# 2. Create the SQLite dev database and load demo data
npm run db:setup

# 3. Start the API (port 3001) and the web app (port 5173) together
npm run dev
```

Then open **http://localhost:5173**.

Other useful commands:

```bash
npm run build      # type-check + production build of both workspaces
npm test           # run the server and client test suites
npm run seed       # re-seed demo data (also resets passwords to the demo values)
npm run db:studio  # browse the database with Prisma Studio
```

> **Windows note:** if PowerShell blocks `npm`, use `npm.cmd` and `npx.cmd` instead.

### Provisioning a chemist

Chemist accounts are deliberately *not* creatable through the public sign-up form:

```bash
npm run provision:chemist -w server -- \
  --email pharmacy@example.com \
  --password "Str0ngPass!" \
  --name "Pharmacy Owner" \
  --shop "WellLife Pharmacy" \
  --license "MH-PH-2024-0001" \
  --address "12 Main St" \
```

## Environment variables

A development `server/.env` is included with safe local defaults, so the app runs as-is.
All values it sets are listed below. In production the app **refuses to start** without a
PostgreSQL `DATABASE_URL` and a real `SESSION_SECRET` (see `server/src/config.ts`).

| Variable | Development default | Purpose |
|----------|--------------------|---------|
| `DATABASE_URL` | `file:./dev.db` | Database connection string; **must be a `postgresql://` URL in production** |
| `PORT` | `3001` | API port |
| `NODE_ENV` | `development` | Environment name; `production` enables secure cookies, the Postgres session store, and config validation |
| `SESSION_SECRET` | dev placeholder | **Must be a long random value in production** (boot fails otherwise) |
| `CORS_ORIGIN` | `http://localhost:5173,http://localhost:4173` | Comma-separated list of allowed origins |
| `COOKIE_SAME_SITE` | `lax` (`none` when `NODE_ENV=production`) | Set to `none` when the client is on a different domain than the API |
| `RATE_LIMIT_WINDOW_MS` | `900000` | Rate-limit window (15 min) |
| `RATE_LIMIT_MAX` | `300` | Max requests per window |
| `AUTH_RATE_LIMIT_MAX` | `20` | Max auth requests per window |

The client reads one optional build-time variable:

| Variable | Default | Purpose |
|----------|---------|---------|
| `VITE_API_BASE_URL` | empty (same origin) | API base URL, e.g. `https://mediremind-api.onrender.com`. Required when the client and API are on different domains (also used for the CSV export link). |

## How the domain logic works

### Inventory arithmetic

The rule the whole app is built around:

```
Remaining = Previous Remaining − Quantity Used by Recorded Doses + Confirmed Refill Quantity
```

- Only a **TAKEN** dose deducts stock, by `quantityPerDose`.
- **SKIPPED** and **SNOOZE** never change stock.
- Stock never goes negative, even if `quantityPerDose` exceeds the remaining count — the
  deduction is capped at what is actually left.
- Dose actions are idempotent: a dose that already has a recorded status cannot be
  re-recorded, so a double tap cannot deduct twice.
- **Only a confirmed chemist refill increases stock.** A pending, accepted, or "ready"
  refill changes nothing. Manual stock corrections are recorded as adjustments and are
  clearly separated from refill transactions in the ledger.

Because every deduction and addition is persisted as an explicit ledger entry (dose log
delta or refill transaction), the current quantity is fully auditable rather than a single
opaque number.

### Refill statuses

```
PENDING ──▶ ACCEPTED ──▶ READY ──▶ COMPLETED
   │            │
   ├────────────┴──▶ REJECTED
   │            │
   └────────────┴──▶ CANCELLED
```

Invalid transitions are rejected with `409`. Completing a refill uses a guarded
`updateMany` that only matches a still-open request, plus a unique constraint on
`refillRequestId`, which together make double-confirmation impossible even under
concurrent requests.

### Automatic refill alerts

When a dose is recorded and the remaining quantity reaches or falls below the medication's
refill threshold, MediRemind raises a refill alert and — if the patient has a linked
chemist shop — automatically creates a refill request. Duplicate alerts and duplicate
requests are prevented. When stock becomes healthy again (a confirmed refill, a manual
adjustment, or an edited threshold) the open alert is resolved automatically.

### Reminders

A lightweight in-process scheduler polls for due doses and creates in-app notifications.
Snoozing a dose re-arms it so the reminder fires again after the snooze interval.

## Roles & permissions

Authorization is enforced **server-side** on every sensitive route, not just hidden in the UI.

| Capability | Patient | Caregiver | Chemist |
|------------|:-------:|:---------:|:-------:|
| Self-register | ✅ | ✅ | ❌ (provisioned) |
| Manage own medications | ✅ | ❌ | ❌ |
| Record doses | ✅ | ❌ | ❌ |
| Adjust own inventory | ✅ | ❌ | ❌ |
| Request refills | ✅ | ❌ | ❌ |
| View shared patient summary | ❌ | ✅ (scoped) | ❌ |
| Invite/revoke caregivers | ✅ | ❌ | ❌ |
| See refill requests | own only | ❌ | own shop only |
| Complete a refill (adds stock) | ❌ | ❌ | ✅ |
| Access another patient's data | ❌ | ❌ | ❌ |

Every query is scoped to the signed-in user or to an explicitly authorized link, so
cross-tenant access returns "not found" rather than leaking that a record exists.

## Database: SQLite (dev) vs PostgreSQL (production)

Development uses **SQLite** (`server/prisma/dev.db`) so the project runs with zero external
services. For **production** a PostgreSQL schema is provided and both are generated from one
source of truth.

`server/prisma/schema.prisma` is the SQLite schema and the single source of truth.
`schema.postgres.prisma` is generated from it (only the `provider` line differs):

```bash
cd server
npm run db:use:postgres   # regenerate schema.postgres.prisma from schema.prisma
npm run db:push:postgres  # create tables in the Postgres database
```

The schema stays portable to PostgreSQL because:

- No native enums, `Json`, or `Decimal` columns are used; allowed values are enforced with
  Zod and documented in `schema.prisma` comments.
- Identifiers use CUIDs rather than auto-increment integers.
- All monetary/quantity math uses plain integers/floats with explicit rounding.

One SQLite-specific note is already handled in the code: nested interactive transactions
must use the transaction client (`tx`) rather than the global Prisma client, which
otherwise deadlocks on SQLite. The services do this consistently. (PostgreSQL tolerates the
global client, but the same code works on both.)

See **[DEPLOYMENT.md](DEPLOYMENT.md)** for the full Render + Netlify walkthrough.

The repo ships deployment configuration for a two-service setup:

run against a live PostgreSQL server** during development (no Postgres was available in the
development environment). See [Honest limitations](#honest-limitations).

## Honest limitations

These are real constraints of this build, documented rather than papered over.

- **PostgreSQL is supported but not verified here.** The Postgres schema and session store
  are implemented and validated (`prisma validate`), but this project was developed and
  tested against SQLite only, because no PostgreSQL server was available in the development
  environment. Treat the Postgres path as untested-in-anger until you run it once yourself.
- **Sessions are in memory in development** (`memorystore`). In production the app uses a
  PostgreSQL-backed store (`connect-pg-simple`, table `user_sessions`) so sessions survive
  restarts, and it refuses to start in production without a PostgreSQL `DATABASE_URL` and a
  real `SESSION_SECRET`. Development still signs everyone out on restart.
- **Reminders are in-process.** The scheduler runs inside the API process and produces
  in-app notifications. There is no email, SMS, or push delivery, and no guarantee a
  reminder fires exactly on time — precision depends on the host staying up and the poll
  interval.
- **No CSRF tokens.** Cross-site POSTs are mitigated by cookie `SameSite` attributes
  (`lax` in development, `none` + `secure` in production, where `SameSite=none` offers no
  CSRF protection on its own). There is no token-based CSRF defence; add one before
  handling anything sensitive.
- **TLS is the deployment's job.** Cookies are `httpOnly` and `secure` in production, so the
  app expects to be served over HTTPS. Terminating TLS (and setting a strong
  `SESSION_SECRET`) is the host's responsibility; this repo does not include certificates.
- **Chemist provisioning is a CLI script**, standing in for an administrative back office.
  There is no admin UI.
- **No load or penetration testing has been performed.** The test suite covers behaviour and
  authorization rules, not performance or adversarial security.
- **Not a medical device.** MediRemind records what a prescriber has specified. It never
  suggests changing a prescribed dose and is not a substitute for professional care.
- **All demo data is fictional.** Names, pharmacies, phone numbers and medications are
  invented for demonstration.

## What is intentionally out of scope

- Payment, insurance, or delivery logistics.
- Integrations with pharmacy or hospital systems (no HL7/FHIR).
- Prescription image upload or OCR.
- Multi-language and full WCAG audit (the UI is built responsively with labelled controls
  and keyboard-reachable actions, but a formal accessibility audit has not been done).
